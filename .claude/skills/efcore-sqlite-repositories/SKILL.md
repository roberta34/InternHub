## 2. Entity facts (verify — do not assume)

### Student (`InternHub.Domain.Students` namespace)
- `sealed class`
- Properties include `Guid Id`, `string FullName`, `string Email`
- Navigation: `IReadOnlyCollection<InternshipCandidacy> InternshipCandidacies` backed by `private readonly List<InternshipCandidacy> _internshipCandidacies`
- Constructor guards against `Guid.Empty`

### Offer (`InternHub.Api.Domain.Offers` namespace)
- `class` (not sealed)
- Properties: `Guid Id`, `string Title`, `string CompanyName`, `string Requirements`, `DateTime Deadline`, `int MaximumAvailableSlots`, `bool IsClosed`, `int Version`
- `Version` has a `private set`; it starts at `0` and changes **only** through Domain methods (Section 11)
- There is **no** `AcceptedCount` column: occupied slots are computed by counting candidacies with `Status == Accepted`
- Navigation: `IReadOnlyCollection<InternshipCandidacy> InternshipCandidacies` backed by `private readonly List<InternshipCandidacy> _internshipCandidacies`
- Constructor generates its own `Id` via `Guid.NewGuid()`

### InternshipCandidacy (`InternHub.Api.Domain.InternshipCandidacies` namespace)
- `sealed class`
- Properties: `Guid Id`, `Guid StudentId`, `Guid OfferId`, `DateTime ApplicationDate`, `InternshipCandidacyStatus Status`
- Constructor rejects empty ids and undefined `Status` values (`Enum.IsDefined`)
- `IsActive` is **computed in C#** (`Submitted | Shortlisted | Accepted | Waitlisted`). EF Core cannot translate it — queries must list the statuses explicitly
- Transitions return `bool` (`true` = transition applied):
  - `Shortlist()` — only from `Submitted`
  - `Accept(bool hasAvailableSlot)` — from `Submitted` or `Shortlisted`; sets `Accepted` when a slot is available, otherwise `Waitlisted`
  - `Reject()`, `Withdraw()` — from `Submitted` or `Shortlisted`
- No transition leaves `Accepted`, so the number of accepted candidacies of an offer never decreases
- No navigation references back to `Student` or `Offer` (FK-only join entity)

### Relationship

Student  1 ---- * InternshipCandidacy * ---- 1  Offer

using InternHub.Api.Domain.InternshipCandidacies;

using InternHub.Domain.Students;

namespace InternHub.Api.Infrastructure.Persistence;

    public DbSet<Offer> Offers => Set<Offer>();
    public DbSet<InternshipCandidacy> InternshipCandidacies => Set<InternshipCandidacy>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)

- `DbSet<T>` properties use expression-body `=> Set<T>()`.
- `OnModelCreating` delegates entirely to `IEntityTypeConfiguration<T>` classes.
- No business logic in `DbContext`.

### 8.1 StudentConfiguration

```csharp
public sealed class StudentConfiguration : IEntityTypeConfiguration<Student>
{
    public void Configure(EntityTypeBuilder<Student> builder)
    {
        builder.HasKey(s => s.Id);

        builder.Property(s => s.Id)
               .HasConversion<string>()
               .IsRequired();

        builder.Property(s => s.FullName)
               .HasMaxLength(200)
               .IsRequired();

        builder.Property(s => s.Email)
               .HasMaxLength(320)
               .IsRequired();

        builder.HasIndex(s => s.Email)
               .IsUnique();

        builder.HasMany(s => s.InternshipCandidacies)
               .WithOne()
               .HasForeignKey(c => c.StudentId)
               .OnDelete(DeleteBehavior.Cascade);

        builder.Navigation(s => s.InternshipCandidacies)
               .UsePropertyAccessMode(PropertyAccessMode.Field);
    }
}
```

**GUID persistence rule**: store every `Guid` primary and foreign key as `string`
with `.HasConversion<string>()`. SQLite has no native UUID type.

**Private backing field rule**: navigations backed by `private readonly` lists use
`.UsePropertyAccessMode(PropertyAccessMode.Field)`.

### 8.2 OfferConfiguration

```csharp
public sealed class OfferConfiguration : IEntityTypeConfiguration<Offer>

    {
        builder.HasKey(o => o.Id);

               .IsRequired();

        builder.Property(o => o.Deadline).IsRequired();

        builder.Property(o => o.IsClosed).IsRequired();

        builder.Property(o => o.Version)
               .IsConcurrencyToken();

               .WithOne()

               .UsePropertyAccessMode(PropertyAccessMode.Field);
    }

```

`.IsRowVersion()` is for SQL Server `rowversion` columns. Do NOT use it for SQLite;
`.IsConcurrencyToken()` is the correct annotation. This line is already in place —
the concurrency policy (Section 11) depends on it, so never remove it.

## 9. EfCoreStudentRepository

```csharp
public sealed class EfCoreStudentRepository(InternHubDbContext db) : IStudentRepository
{
    public bool Add(Student student)
    {
        db.Students.Add(student);
        try
        {
            db.SaveChanges();
        }
        catch (DbUpdateException exception)
            when (IsDuplicateStudentEmailConflict(exception))
        {
            return false;
        }

        return true;
    }

    private static bool IsDuplicateStudentEmailConflict(DbUpdateException exception) =>
        exception.InnerException is SqliteException { SqliteErrorCode: 19 } sqliteException
        && sqliteException.Message.Contains("Students.Email", StringComparison.OrdinalIgnoreCase);

    public Student? GetById(Guid id) =>
        db.Students.Include(s => s.InternshipCandidacies).FirstOrDefault(s => s.Id == id);

    public IReadOnlyList<Student> GetAll() =>
        db.Students.Include(s => s.InternshipCandidacies).ToList();

    public bool Update(Student student)
    {
        if (!db.Students.Any(s => s.Id == student.Id)) return false;

        db.Students.Update(student);
        try
        {
            db.SaveChanges();
        }
        catch (DbUpdateException exception)
            when (IsDuplicateStudentEmailConflict(exception))
        {
            return false;
        }

        return true;
    }

    public bool Delete(Guid id)
    {
        var student = db.Students.FirstOrDefault(s => s.Id == id);
        if (student is null) return false;

        db.Students.Remove(student);
        db.SaveChanges();
        return true;
    }
}
```

`Add` and `Update` translate only the known SQLite unique-constraint violation for
`Students.Email` into `false`, so CreateStudent / UpdateStudent can return
`Result.Conflict` (HTTP 409). Do not catch every `DbUpdateException`, every SQLite
error code 19, or an arbitrary message; unrelated failures must propagate. A rejected
update leaves the row unchanged.

## 10. EfCoreOfferRepository

```csharp
public sealed class EfCoreOfferRepository(InternHubDbContext db) : IOfferRepository
{
    public bool Add(Offer offer)
    {
        db.Offers.Add(offer);
        db.SaveChanges();
        return true;
    }

    public Offer? GetById(Guid id) =>
        db.Offers.Include(o => o.InternshipCandidacies).FirstOrDefault(o => o.Id == id);

    public IReadOnlyCollection<Offer> GetAll() =>
        db.Offers.Include(o => o.InternshipCandidacies).ToList();

    public bool Update(Offer offer)
    {
        if (!db.Offers.Any(o => o.Id == offer.Id)) return false;

        db.Offers.Update(offer);
        try
        {
            db.SaveChanges();
        }
        catch (DbUpdateConcurrencyException exception)
        {
            throw new OfferConcurrencyException(offer.Id, exception);
        }

        return true;
    }

    public bool Delete(Guid id)
    {
        var offer = db.Offers.FirstOrDefault(o => o.Id == id);
        if (offer is null) return false;

        db.Offers.Remove(offer);
        db.SaveChanges();
        return true;
    }
}
```

`Update` translates `DbUpdateConcurrencyException` into the Domain-level
`OfferConcurrencyException` (single-row conflict style, Section 11.3).

## 11. Offer.Version — optimistic concurrency policy (applies to the whole team)

### 11.1 What Version protects

`Offer.Version` is the single optimistic-concurrency token of the Offer aggregate.
EF Core emits every `UPDATE Offers` as
`... WHERE Id = @id AND Version = @originalVersion`. If another request saved the offer
after it was read, the statement matches 0 rows and EF Core throws
`DbUpdateConcurrencyException`. The database itself raises no error — EF Core detects
the conflict because it expected 1 affected row.

### 11.2 Who changes Version

`Version` changes **only** through Domain methods on `Offer` (generated by the cqrs skill):

| Domain method | When | Introduced |
|---|---|---|
| `Update(...)` | recruiter edits the offer | Sprint 2 |
| `Close()` | recruiter closes the offer | Sprint 3 |
| `RegisterAcceptedSlot()` | a candidacy transitions to `Accepted` (consumes a slot) | Sprint 4 |

Persistence code never writes `Version` directly (no `db.Entry(...).Property(...)`,
no raw SQL, no `ExecuteUpdate` on `Version`).

**Rule for future features:** if a decision depends on offer-level state that concurrent
requests can change (slots, closure, future capacity rules), the operation must call an
`Offer` method that increments `Version`, and must save that offer in the **same**
`SaveChanges` / transaction as the rows it changes. This turns a multi-row rule into a
conflict on one shared row, which every relational database detects — not only SQLite.

### 11.3 Two ways to react to a Version conflict

| Style | Used by | Reaction |
|---|---|---|
| Single-row update | `EfCoreOfferRepository.Update` → `UpdateOfferHandler`, `CloseOfferHandler` | translate to `OfferConcurrencyException`; handler returns `Result.Conflict` (409); the client re-reads and retries |
| Atomic service | `EfCoreAtomicCandidacyDecision` (Section 21) | clear the change tracker, re-read, re-evaluate the rule, retry (max 3); after the last attempt return a typed `ConcurrencyConflict` result (409) |

Use the single-row style when the client sent the expected `Version`. Use the atomic
style when the server can safely re-evaluate the decision itself.

### 11.4 Handler pattern for UpdateOffer (generated by the cqrs skill)

1. Read the stored `Offer` from the repository.
2. Compare the incoming `Version` with `offer.Version`; if different, return `Result.Conflict` before saving.
3. Call `offer.Update(...)` (increments `Version`).
4. Call `repository.Update(offer)`.
5. Catch `OfferConcurrencyException` and return `Result.Conflict`.

Handlers never reference `Microsoft.EntityFrameworkCore`, `DbContext`, `DbSet<T>` or SQLite.

## 12. DI registration — PersistenceExtensions

```csharp
public static class PersistenceExtensions
{
    public static IServiceCollection AddPersistence(
        this IServiceCollection services,
        IConfiguration configuration)
    {
        var connectionString = configuration.GetConnectionString("InternHub")
            ?? "Data Source=internhub.db";

        services.AddDbContext<InternHubDbContext>(options =>
            options.UseSqlite(connectionString));

        services.AddScoped<IStudentRepository, EfCoreStudentRepository>();
        services.AddScoped<IOfferRepository, EfCoreOfferRepository>();
        services.AddScoped<IInternshipCandidacyRepository, EfCoreInternshipCandidacyRepository>();
        services.AddScoped<IAtomicCandidacySubmission, EfCoreAtomicCandidacySubmission>();
        services.AddScoped<IAtomicCandidacyDecision, EfCoreAtomicCandidacyDecision>();

        return services;
    }
}
```

- `InternHubDbContext` is Scoped (the `AddDbContext` default): one context per HTTP request.
  Two concurrent requests therefore read independently — which is exactly why
  multi-row rules need Section 20.
- Every repository and atomic service is registered as **Scoped** here, never in a
  feature module. Feature modules register handlers and endpoints only.
- Add one line per new service; never reorder or remove existing registrations.

## 20. Atomic multi-row persistence services (shared pattern)

### 20.1 When to use

Use an atomic service when one business decision must **read several rows, check a rule
and write**, and concurrent requests could otherwise all pass the check on stale data.
Examples: one active candidacy per student and offer, at most five active candidacies per
student, accepted candidacies not exceeding `MaximumAvailableSlots`.

Do not split such a decision across several repository calls — each would save separately.

### 20.2 Mandatory structure

```
public async Task<TResult> <Operation>Async(..., CancellationToken cancellationToken = default)
    for attempt = 1..MaximumAttempts (3):
        db.ChangeTracker.Clear();                         // fresh data on every attempt
        try   { return await <Operation>AttemptAsync(...); }
        catch (<documented, filtered exceptions>)  { retry or map to a typed result }

private async Task<TResult> <Operation>AttemptAsync(...)
    await using var transaction = await db.Database.BeginTransactionAsync(ct);
    load + check rules (early return = typed failure; the transaction rolls back on disposal)
    call Domain methods (never set entity state by hand)
    await db.SaveChangesAsync(ct);                       // exactly once
    await transaction.CommitAsync(ct);
    return typed success;
```

- Constants: `MaximumAttempts = 3`, `RetryDelayMilliseconds = 25`,
  `SqliteBusyErrorCode = 5`, `SqliteLockedErrorCode = 6`.
- SQLite contention (5 = BUSY, 6 = LOCKED) may arrive as `SqliteException` or as
  `DbUpdateException.InnerException`; detect both.
- The service uses `InternHubDbContext` directly; it never calls repositories.
- Status filters list statuses explicitly (R12).
- The service receives ids, not entities, and loads everything inside the transaction.

### 20.3 Existing service — AtomicSubmission (Apply, Sprint 4)

`EfCoreAtomicCandidacySubmission` implements `IAtomicCandidacySubmission.SubmitAsync(studentId, offerId)`.
**Do not modify it** unless the request explicitly targets it.

What it guarantees and how:

| Rule | Protection |
|---|---|
| Student / offer exist, offer not closed, deadline not passed | checked inside the transaction |
| One active candidacy per (student, offer) | check inside the transaction **+** partial unique index (SQLite 19 / 2067 is caught, verified and mapped to `DuplicateActive`) |
| At most 5 active candidacies per student | count inside the transaction; relies on SQLite serialising write transactions |
| Contention | retry on 5 / 6; after the last attempt an `InvalidOperationException` with a clear message |

Provider note: the five-candidacy limit has no shared row and no index behind it. On a
provider that does not serialise write transactions (e.g. PostgreSQL at Read Committed),
it would need a shared concurrency token (for example a `Version` on `Student`, following
Section 11.2). Keep this in mind if the provider changes; it is not required while the
project runs on SQLite.

## 21. AtomicDecision — atomic Accept / Shortlist / Reject (Sprint 4)

### 21.1 Purpose

Fixes the REVIEW.md Major finding at `DecideInternshipCandidacyHandler.cs:38`: two concurrent
accepts on the last slot could both persist `Accepted`. After this change at most one becomes
`Accepted`; the other is re-evaluated and becomes `Waitlisted` (US5 AC3, BR-09, BR-10).

### 21.2 Inputs (produced by the cqrs skill, §13.5)

must exist with the members listed in cqrs §13.5. If any is missing, stop and report; do not
create it from this skill. The handler-side status mapping is defined there, not here.

### 21.3 Output

| File | Change |

### 21.4 Algorithm (one attempt, inside the Section 20.2 structure)

1. Load the candidacy by id (tracked). Missing → `CandidacyNotFound`.
2. `Accept`: load the offer by `candidacy.OfferId` without `Include` (missing → `OfferNotFound`);
   count candidacies of that offer with `Status == Accepted`; call
   `candidacy.Accept(acceptedCount < offer.MaximumAvailableSlots)`; **only if** it returned `true`
   and the new status is `Accepted`, call `offer.RegisterAcceptedSlot()`.
3. `Shortlist` / `Reject`: call the Domain method; the offer is neither loaded nor modified.
4. A Domain method returned `false` → `InvalidTransition`.
5. One `SaveChangesAsync` + `CommitAsync` → `Success(candidacy)`.

Retries: `DbUpdateConcurrencyException` and SQLite 5 / 6 are retried (Section 20.2); after the
last attempt the result is `ConcurrencyConflict`, never an exception.

Do **not** check `IsClosed` or `Deadline` (BR-04, BR-11). A concurrent `Close()` or `Update(...)`
also changes `Version`, so an accept racing with them is retried on fresh data.

### 21.5 Example of expected output (the slot-consuming branch only)

```csharp
var acceptedCount = await db.InternshipCandidacies.CountAsync(
    c => c.OfferId == offer.Id && c.Status == InternshipCandidacyStatus.Accepted,
    cancellationToken);

changed = candidacy.Accept(acceptedCount < offer.MaximumAvailableSlots);

if (changed && candidacy.Status == InternshipCandidacyStatus.Accepted)
    offer.RegisterAcceptedSlot();   // same SaveChanges: Offers row guarded by Version
```
