# Unit Testing Skill - InternHub

Generate **unit tests only**, for one requested Domain entity or CQRS vertical slice at a time. Each team member owns tests for their own slices. Do not write or modify production code with this skill.

If generated tests are wrong, improve **this SKILL.md**, then **regenerate** the affected tests. Never manually patch generated test code.

## 1. Before generating - inspect the real code

Read, in this order:

1. `tests/InternHub.Tests/InternHub.Tests.csproj` and existing unit-test conventions.
2. The requested `Domain/<Aggregate>/` type or `Features/<Aggregate>/<UseCase>/` handler, its command/query and handler interface.
3. The repository interface actually used by the handler and any existing hand-written fake.
4. `Features/Shared/Result.cs` (or the actual Result definition) and the relevant Domain validation rules.
5. Existing tests for that type or slice, to avoid duplicate test classes and to preserve meaningful scenarios.

Never invent public methods, signatures, properties, constructors, Result members, or business rules. If required code has not yet been generated by the earlier skills, **report the blocker** instead of guessing.

**CQRS compatibility:** The agreed CQRS skill defines `Handle(...)` returning `Result<T>` for synchronous repositories and `HandleAsync(...)` only where the real repository interface is asynchronous. Its example uses `result.Status` with `ResultStatus.Success`, `Validation`, `NotFound`, or `Conflict`. Verify the real implementation before generating: do not use `IsNotFound`, `IsSuccess`, or `HandleAsync` unless they actually exist.

## 2. Required framework and naming

- Use **xUnit** and **FluentAssertions 7.x** (pin to version `7.*` in the test project; do not upgrade to 8.x).
- Name test classes `<ClassUnderTest>Tests`, e.g. `CreateOfferHandlerTests` or `OfferTests`.
- Name test methods `Given_<state>_When_<action>_Then_<expected>`.
- Use `[Fact]` for one scenario and `[Theory]` with `[InlineData]` for variations of the same behavior.
- Organize every test into `// Arrange`, `// Act`, `// Assert`, with a **blank line between blocks**.
- Check **one observable behavior per test**. Multiple assertions are allowed when they establish the same behavior.
- Prefer behavior and state assertions to verifying implementation details.
- Do not put `if`, `for`, `foreach`, `while`, or `switch` inside test methods.

## 3. Test isolation and fakes

- For a handler, use a small **hand-written fake** implementing its **existing** repository interface; never add Moq, NSubstitute, or other mocking libraries.
- Implement every required interface member using the signatures read from source. A fake must compile and support the test scenario; do not generate `NotImplementedException` placeholders for paths the test exercises.
- Create fresh dependencies and state for each test; do not rely on shared mutable data, execution order, or other tests.
- Unit tests do **not** start HTTP hosts, access SQLite/EF Core, files, Ollama, networks, or other external services.
- Use `Guid.NewGuid()` for valid generated IDs; reuse the same variables through the scenario. `Guid.Empty` is valid test input only when testing its rejection.
- For time-dependent behavior, inject `TimeProvider` or the project's existing controllable clock abstraction and use a fake clock. Never depend on `DateTime.Now`, `DateTime.UtcNow`, sleeping, or wall-clock timing in tests.
- If testability requires a production change, report it. Do **not** edit production code using this skill.

## 4. Behaviors to cover

- **Domain:** valid construction, invalid and boundary inputs, updates, state transitions, and reachable business invariants present in the real code.
- **Handlers:** success, validation, not-found, and conflict **only when applicable to the actual use case**.
- Validate that commands change state correctly and queries return correct data without changing it.
- For expected errors, check the returned Result status and relevant message/data, not an exception (unless testing the Domain's documented exception behavior itself).
- Do not generate tests merely asserting non-null objects, duplicated behaviors, or private implementation details.
- Aim for **100% Domain and handler coverage across InternHub**, including meaningful branches. Do not remove meaningful tests or exclude production behavior to inflate coverage.
- HTTP status codes, `Location` headers, and database persistence belong to the **integration-testing** skill.

## 5. Folder structure

Mirror the production path under `tests/InternHub.Tests/Unit/`:

```text
src/InternHub.Api/Domain/Offers/Offer.cs
  -> tests/InternHub.Tests/Unit/Domain/Offers/OfferTests.cs

src/InternHub.Api/Features/Offers/CreateOffer/CreateOfferHandler.cs
  -> tests/InternHub.Tests/Unit/Features/Offers/CreateOffer/CreateOfferHandlerTests.cs

src/InternHub.Api/Features/Offers/GetOfferById/GetOfferByIdHandler.cs
  -> tests/InternHub.Tests/Unit/Features/Offers/GetOfferById/GetOfferByIdHandlerTests.cs
```

Use the namespaces found in source. Update or replace obsolete Sprint 1 tests only for the requested ownership area; do not leave duplicate test class definitions. Put reusable hand-written fakes in an appropriate test-support folder if more than one test needs them.

## 6. Example of expected output

The following illustrates a **Domain unit test** based on the Offer constructor and `Version` rule documented by the CQRS skill. Before generating real tests, verify those members in the current source code.

```csharp
using FluentAssertions;
using InternHub.Api.Domain.Offers;
using Xunit;

namespace InternHub.Tests.Unit.Domain.Offers;

public sealed class OfferTests
{
    [Fact]
    public void Given_ValidOfferData_When_CreatingOffer_Then_StartsWithVersionZero()
    {
        // Arrange
        var deadline = new DateTime(2027, 1, 15, 0, 0, 0, DateTimeKind.Utc);

        // Act
        var offer = new Offer("Backend Intern", "Example Co", "C#", deadline, 2);

        // Assert
        offer.Version.Should().Be(0);
    }
}
```

For handler tests, use the **real handler contract**. If the handler is synchronous and returns `Result<T>`, the assertion should follow this pattern (with an actual compiled fake repository in the generated test support code):

```csharp
// Act
var result = handler.Handle(new GetOfferByIdQuery(offerId));

// Assert
result.Status.Should().Be(ResultStatus.NotFound);
```

Do not copy this pattern blindly if the inspected implementation differs.

## 7. Verify and report

Before finishing, check:

- [ ] The real production contracts were inspected; test code compiles against them.
- [ ] xUnit and FluentAssertions `7.*` are used.
- [ ] Test names follow `Given_..._When_..._Then_...`.
- [ ] Each test separates Arrange / Act / Assert with blank lines.
- [ ] One meaningful behavior is tested per case, without loops or branches in the test body.
- [ ] Fakes implement the actual interfaces; no mocking library or external service is needed.
- [ ] IDs and time are controlled; tests are independent.
- [ ] Expected Result statuses and applicable Domain outcomes are checked.
- [ ] Only the requested owner's unit tests and their test-support files were changed.

Run `dotnet test tests/InternHub.Tests/InternHub.Tests.csproj` when the repository is available. If tests fail due to generated code, record the actual failure, improve **this SKILL.md**, and regenerate tests through the skill. Do not silently patch generated tests.

End with a short report: files created/changed, tested behaviors, command results, coverage gaps, and any blockers. Provide a factual `PROMPTS.md` entry describing the request, skill used, observed output problem, skill revision, reason, and before/after result. **Never claim tests or regeneration were run unless they actually were.**
